# Обход блокировок через CDN (Яндекс Cloud CDN) на Remnawave

Схема: **клиент → CDN (домен-«витрина») → origin (ваш отдельный VPS) → nginx → Xray XHTTP**.
Для провайдера трафик выглядит как обычная загрузка файлов с адреса российского CDN, поэтому блокировка IP вашего сервера не мешает.
Всё управляется из панели Remnawave: подписки пользователей получают дополнительную локацию автоматически.

> Честно о ограничениях: такая схема медленнее обычного Reality (трафик режется на мелкие запросы через посредника).
> Условия CDN-провайдеров могут запрещать подобное использование — аккаунт может быть заблокирован. Это резервный маршрут, а не замена основным нодам.
> Скрипт проверен на моках панели; работу с реальным Яндекс CDN нужно проверить вам по шагам ниже.

## Что нужно
- отдельный VPS (Ubuntu 22.04/24.04, порты 80 и 443 свободны) — это **origin**;
- домен; аккаунт Яндекс Cloud с платёжным аккаунтом и разделом Cloud CDN;
- установленная панель Remnawave и её API-токен.

## Шаг 1. DNS для origin
Создайте A-запись `cdn.example.com → IP origin-сервера` (без проксирования). **Её нельзя удалять**: по ней CDN ходит за данными, и по ней продлевается сертификат.

## Шаг 2. Запуск установщика на origin-сервере
```bash
sudo bash install-cdn.sh --panel https://panel.example.com --token API-ТОКЕН \
     --origin cdn.example.com --name Yandex-CDN --country RU --yes
```
Скрипт: ставит nginx, certbot и Docker; получает сертификат; делает страницу-заглушку; настраивает проксирование секретного пути
(`/api/getFile`) во внутренний Xray; создаёт в панели профиль `VAYLO-CDN` (VLESS + XHTTP, режим packet-up), ноду и добавляет её inbound в сквад `VAYLO`.
В конце он печатает команду проверки — должна вернуть `400` (это нормально: запрос дошёл до VPN, но без ключа).

## Шаг 3. Сертификат и ресурс в Яндекс Cloud CDN
Консоль: console.yandex.cloud → выберите каталог.

**3.1. Сертификат для домена-витрины** (раздел **Certificate Manager**):
«Добавить сертификат» → «Сертификат Let's Encrypt» → домен `yacdn.example.com`, тип проверки — **DNS**. На вкладке сертификата появится
«CNAME-запись» для проверки: создайте её у своего DNS-хостера (имя вида `_acme-challenge.yacdn`; других записей с этим именем быть не должно).
Дождитесь статуса **Issued** (обычно несколько минут).

**3.2. Ресурс** (раздел **Cloud CDN** → «Создать ресурс»):
- блок «Контент»: «Доступ к контенту» — включить; «Запрос контента» — с одного источника; «Тип источника» — **Сервер**;
- «Доменное имя источника»: `cdn.example.com`; «Протокол для источников»: **HTTPS**;
- «Доменное имя» (витрина): `yacdn.example.com`;
- блок «Дополнительно»: «Тип сертификата» — из Certificate Manager (выберите сертификат из 3.1);
  «Использовать заголовок Host» — **Свое значение** → `cdn.example.com`;
- «Продолжить»; на шаге «Кеширование» **выключите кеширование** (кеширование на стороне CDN-серверов), остальное можно оставить по умолчанию.

**3.3. Разрешить метод POST (критично!).** XHTTP отправляет данные от клиента запросами POST, а Яндекс CDN по умолчанию их блокирует (ответ 405).
Откройте ресурс → вкладка «HTTP-заголовки и методы» → «Редактировать» → «Методы запросов от клиентов» → «Разрешенные методы». Если POST там
включить нельзя, по документации Яндекса его включает **техподдержка** по обращению (https://center.yandex.cloud/support): опишите, для чего нужен POST. Решение за Яндексом, и они могут отказать.
Изменения применяются до 15 минут.

**3.4.** На странице ресурса скопируйте значение `cname` (вида `xxxx.topology.gslb.yccdn.ru`).

## Шаг 4. DNS для витрины
`CNAME yacdn → значение от Яндекса`. Подождите 10–30 минут (новый ресурс разворачивается по сети — до этого возможны 403/404, ничего не переделывайте).
Проверка с любого сервера:
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://yacdn.example.com/api/getFile/
```
Когда придёт `400` — цепочка работает. Проверка POST: `curl -s -o /dev/null -w "%{http_code}\n" -X POST https://yacdn.example.com/api/getFile/` — `405` значит, метод ещё заблокирован (см. шаг 3.3), `400` — всё в порядке.

## Шаг 5. Хост для подписок
Запустите установщик на origin ещё раз с теми же параметрами и добавьте `--cdn-domain yacdn.example.com`.
Он создаёт в панели хост: адрес и SNI `yacdn.example.com`, порт 443, TLS, fingerprint chrome, ALPN `h2,http/1.1`, путь туннеля.
Пользователи после обновления подписки увидят новую локацию (Happ, Incy и другие клиенты с поддержкой XHTTP).

## Если не работает
Проверяйте цепочку по порядку на origin-сервере (первые три ответа должны быть `400`):
```bash
curl -sk -o /dev/null -w "1_xray=%{http_code}\n"  http://127.0.0.1:2053/api/getFile/
curl -sk -o /dev/null -w "2_nginx=%{http_code}\n" https://cdn.example.com/api/getFile/
curl -sk -o /dev/null -w "3_cdn=%{http_code}\n"   https://yacdn.example.com/api/getFile/
```
| Где оборвалось | Что делать |
|---|---|
| 1 даёт 000/502 | нода не запущена: `docker logs remnanode`, в панели статус ноды |
| 2 даёт 404 или 200 с HTML | путь в nginx и в профиле не совпадает; перезапустите установщик |
| 3 даёт 403 | ресурс ещё разворачивается (до 30 минут), либо CDN режет «простой» XHTTP — пересоздайте профиль с флагом `--obfs` |
| POST даёт 405 | у ресурса не разрешён POST — шаг 3.3 |
| 3 даёт 504 | CDN не дождался ответа: проверьте шаги 1–2, выключите буферизацию и кеш у CDN |

Важно:
- **Только режим packet-up** (stream-up CDN обычно буферизует и рвёт).
- Если CDN выдал только технический домен без вашего персонального — используйте флаг `--empty-host`.
- Вместо пинга приложение может показывать «Н/Д» — это норма, судите по тому, открываются ли сайты.
- Чтобы сменить путь или режим, удалите профиль `VAYLO-CDN` в панели и запустите установщик заново.
